# 订单客户名称查询优化

本次实现方案的前三项，不扩大推荐缓存时间，不修改最终建档规则。

## 输入与查重

- 名称推荐保留 300ms 防抖及中文输入法合成保护。
- 客户名称聚焦编辑期间不调用身份查重；离开输入区域后合并 300ms 内变化，再核对最新身份。
- 收件人、电话、地址组成一个编辑区域，区域内部切换不重复查重；离开区域后检查。粘贴识别等程序填入仍触发检查，切换向导步骤时退出编辑状态。
- 同一个身份的在途请求合并；已完成且身份未变的检查在再次聚焦/离开时复用。身份改变立即使之前的结果不可用于勾选建档，迟到响应不能覆盖新身份。
- 查重等待期间不允许跳过检查直接保存；网络失败或 8 秒超时仍可保存订单，但不申请自动建档。8 秒从发出请求开始计算。
- `saveOrders` 和建档事务继续使用完整身份匹配、版本核验与幂等保护。推荐结果不能作为“不重复”的依据。

## 推荐查询

`manageCustomers.search(scope=orderSuggestions)` 改为标准化字段查询：

1. 客户名与别名精确匹配。
2. 不足三位时补前缀匹配。
3. 仍不足三位时补包含匹配。

每一级并行查询客户和别名，每个来源最多读取 20 条，仅投影推荐需要的字段；别名所属客户通过 ID 批量补齐并检查 active 状态。每级最多三次查询，整个推荐最多读取 180 条摘要记录，不分页读完匹配数据，不读取收货资料，不计算资料总数。

返回最多三位客户，保留精确/前缀/包含的优先级。同一匹配层内只对有界候选排序，不承诺全库更新时间排名；大量别名属于同一客户或停用客户时，推荐可能不足三位，完整查找仍可通过“更多操作”。`limit` 限制的是返回记录，不等于底层扫描记录数量；包含匹配仍可能扫描较多索引项，应独立观察其耗时。

依赖索引：

- `customers.cm_status_normalizedDisplayName`：status + normalizedDisplayName。
- `customer_aliases.cm_normalizedName_enabled`：normalizedName + enabled。

2026-09-22 对环境 `cloud1-8gvbotkt966e5e19` 只读核验：两个索引均存在；客户和别名中缺少标准化名称或 normalizationVersion 非 customer-identity-v2 的记录数均为 0。未创建索引或回填业务数据。其它环境上线前仍需检查标准化字段与索引；现有 `customers:schema` 和 `customers:normalization-backfill` 脚本可预览差异。

## 按需资料

推荐只返回客户名称及已命中的别名，并标记 `detailsDeferred: true`。保留 recipients/aliasTotal/recipientTotal 旧字段以兼容响应结构；标记存在时，空地址及计数并不表示没有资料，前端不能据此展示“暂无收货地址”。

“查看别名和收货地址”在点击后调用现有受限 `getOrderSelection` 接口，别名和地址各自分页。选用客户先关联名称；需要收货信息时点击“使用此地址”填入。已有收件信息仍需要确认后替换。已关联客户旁也保留资料入口。旧云函数的完整推荐响应在新前端仍可显示。

## 验证和发布

- `npm run test:customers`：包含有界查询、精确优先、停用客户过滤、按需读取、输入触发、请求合并、迟到响应、超时与重试，以及原有保存/建档事务测试。
- `npm run build`：类型检查与生产构建。
- `node scripts/order-archive-preview/server.cjs`：隔离内存数据的界面验证，不连接生产数据。

本次改动需配套发布前端和 manageCustomers 的 suggestions.js 才能完整生效；无需更新 saveOrders。此文档记录实现和核验要求，不表示已发布到线上。

线上验收应分别记录输入等待、云函数调用和查询阶段耗时，对比首次及重复查询的 p50/p95，并单独检查包含匹配；本地内存测试不能代替线上延迟测量。
