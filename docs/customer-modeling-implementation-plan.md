# 租赁客户建模分步实现计划

> 依据：[客户建模设计方案](./customer-modeling-design.md)
>
> 制定日期：2026-09-05
>
> 状态：阶段 1～4 已完成本地实现及自动化验证；阶段 5～8 待实施。阶段 4 尚未部署或修改生产业务数据，详见[阶段 4 说明](./customer-modeling-phase4.md)。
>
> 执行方式：保留现有基础功能，按以下阶段补齐；每阶段独立提交、验证，再进入下一阶段。

## 1. 制定计划时的基础与差距（2026-09-05）

| 模块 | 当前代码已有 | 本次需要补齐或修正 |
| --- | --- | --- |
| 数据类型 | 客户、别名、收件档案；订单可选关联字段 | `merged` 状态、合并映射、统计、关系、候选和审计类型 |
| `manageCustomers` | 主档、别名、收件档案 CRUD，列表、搜索、详情、`touchRecipient` | 统一匹配、归档、关系、合并撤销、重关联、统计及运维接口 |
| 客户页面 | `/customers` 导航、列表、资料维护、最近 20 条订单 | 分页订单总览、统计、待归档、关系候选、合并撤销和操作记录 |
| 订单表单 | 手工选择客户、别名和收件档案；可保存关联字段 | 远程检索、快捷建档、显式保存别名/新档案、后端校验与统一接入 |
| 衍生订单 | 前端草稿及售后入口已有部分身份继承 | 校验继承对象、解析合并映射、插件普通导入与续租统一匹配、失败补偿 |
| 权限 | `customers:read`、`customers:write` 和页面配置 | `customers:merge`；取消订单页面权限直接开放客户管理页的回退 |
| 测试 | `npm run test:customers`，目前只有 3 个标准化测试 | 匹配、权限、事务、幂等、扫描、归档、合并、统计及订单入口测试 |

需要优先纠正的现状：

- `normalizers.js` 当前删除名称中的全部空白和部分分隔符，与设计中的“空白折叠、分隔符统一”不一致；直接沿用会扩大精确匹配范围。
- 客户 `list`、`search`、`get` 共用较宽的读取权限，订单只读角色也能调用；需要区分客户管理数据与订单表单所需数据。
- 当前列表搜索读取三个集合后在内存筛选，前端默认请求 5,000 条；应改为受限搜索和服务端分页。
- 当前订单写入接受前端关联字段，关联时间和操作人也由前端填写；身份合法性和审计信息应由服务端负责。
- `touchRecipient` 在保存/编辑时由前端调用，缺少按订单去重及并发保护，不能直接作为准确使用次数。

## 2. 实施约束与顺序

所有阶段遵守以下规则：

1. 仅针对 `rental1` / `rental2` 建立本次客户模型，旧订单和旧客户端无需补齐新字段即可继续使用。
2. 修改客户、归档、合并和撤销都不覆盖订单原有名称、收件人、电话和地址快照。
3. 历史订单始终人工确认；新订单只有满足唯一精确匹配才可自动关联。
4. 候选生成和统计更新失败通过补偿恢复，不阻断订单主流程；显式提交非法客户 ID 或越权关联应返回明确错误。
5. 自动匹配开关初始关闭，并设置启用时间或等价的新订单范围，防止补偿扫描把历史订单自动关联。
6. 云函数按独立目录部署：共享逻辑需有明确打包方式，不能依赖未包含在部署包中的父目录文件。

依赖顺序：阶段 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8。

每阶段包含对应后端、必要界面和验收，避免所有后端完成后才发现业务操作无法闭环。

## 3. 阶段 1：统一模型、规则和权限边界

**目标：先确定所有入口共同遵守的契约。**

- [x] 扩展 `src/types/index.ts`，补齐设计文档中的类型；新增字段保持兼容。
- [x] 按设计文档第 12.2 节为 `manageCustomers` 建立显式 action → 权限映射，新增 `customers:merge`；归档和关系维护使用 `customers:write`，人工全量扫描/重建要求操作权限 `*`，内部调用须验证服务身份和业务范围。
- [x] 修改 `PermissionContext.tsx`、`RoleManageTab.tsx` 和权限初始化配置：进入客户页必须具备页面权限，客户数据接口独立校验操作权限。
- [x] `search` 提供订单表单需要的受限结果，`get` 增加 `scope='orderSelection'` 模式；订单新增/编辑角色仅能获取选择所需的启用别名和收件档案，不因此获得订单总览、审计或完整客户管理权限。字段与分页上限遵循设计文档第 12.3 节。
- [x] 统一名称、电话、地址标准化；补充完整电话判定、空值排除、确定性指纹和规则版本。
- [x] 对旧标准化字段制定 dry-run 差异报告和可重跑回填步骤；变更只更新派生字段，不修改原始资料和订单快照。

实施时采用的默认口径，落入代码和测试前需写入接口说明：

| 设计尚未细化的问题 | 计划口径 |
| --- | --- |
| 名称分隔符 | 明确字符映射表，统一后保留分隔边界；不能把 `A B` 与 `AB` 当作完全一致 |
| 电话有效性 | 数字串仅用于标准化；自动匹配另行判断号码完整性。未明确支持的格式只参与展示和人工候选；不静默移除国家码 |
| 收件人姓名 | 使用与名称一致的保守标准化规则 |
| 别名来源渠道 | 保留来源及同客户去重维度；首版不额外作为自动关联硬条件 |
| 统计金额 | 与现有 `getOrderTotalAmount` 口径一致，兼容多货品与旧扁平订单，不把运费或收款拆分重复累加 |
| 预扫描“只读” | 区分纯预览 dry-run（无写入）和候选扫描（仅写候选与任务进度，订单只读） |

**主要文件：** `src/types/index.ts`、`src/contexts/PermissionContext.tsx`、`src/components/RoleManageTab.tsx`、`cloud_functions/initializePermissionSystem/index.js`、`cloud_functions/manageCustomers/normalizers.js`、`cloud_functions/manageCustomers/index.js`。

**验收：** 标准化边界用例通过；匿名和越权请求被拒绝；订单新增/编辑角色仍能选择客户，但不能进入客户管理页或读取管理详情；现有资料可正常维护。

实现与验证记录见[阶段 1 说明](./customer-modeling-phase1.md)。本阶段内部写动作保持关闭，可信服务调用在订单接入阶段实施。

## 4. 阶段 2：构建统一身份匹配与可靠写入基础

**目标：得到可供所有订单入口调用、结果可解释的服务。**

- [x] 拆分 `manageCustomers` 的匹配、客户簇解析、数据访问和审计逻辑，避免继续把所有功能堆入入口文件。
- [x] 实现 `matchIdentity`：返回精确匹配结果、候选客户、评分及逐条证据。
- [x] 同时验证名称/启用别名和同一启用收件档案中的完整姓名、电话、地址，不跨档案拼凑匹配条件。
- [x] 先解析合并映射，再对最终有效客户去重；无匹配、多客户匹配、字段不完整、停用客户均不得自动关联。
- [x] 实现显式关联校验：客户存在且可接收订单；别名和收件档案属于该客户或其有效客户簇，且可供选择。
- [x] 创建客户及初始别名、同客户别名去重等多记录写入采用事务或确定性键与幂等请求记录，覆盖并发创建场景。
- [x] 新增操作审计存储，保存动作、对象 ID、操作人、时间及必要变更摘要；日志不输出完整身份资料。
- [x] 增加集合/索引初始化及核验脚本，覆盖设计第 13 节；后续阶段新增任务、幂等、审计存储也纳入清单。

**验收：** 唯一精确匹配成功；同名、共享电话/地址、分散在不同档案中的字段、多客户匹配均不会误关联；重复提交不重复建档；合并链解析遇到循环或无效目标明确失败。

## 5. 阶段 3：历史扫描和人工归档闭环

**目标：让历史订单能够安全地逐批归档。**

- [x] 实现 `scanUnlinkedOrders`，支持 dry-run、每批最多 100 条、稳定游标、任务状态、断点恢复和错误统计。
- [x] 使用规则版本及身份指纹更新 `customer_link_candidates`，排除已关联或明确忽略的订单，扫描不写订单归属。
- [x] 保存组内订单的独立处理结果、被拒绝的推荐客户及证据版本。原设计的单个 `status` 不足以表达部分拆分和拒绝某一推荐，需要补充成员记录或等价结构。
- [x] 组内订单过多时使用分页成员存储，避免无限增长的 `orderIds` 超过单文档限制。
- [x] 实现 `listLinkCandidates`、`resolveLinkCandidate`：新建客户、归入已有客户、选择新增别名/档案、部分订单拆分、忽略并填写原因、拒绝某个推荐。
- [x] 确认时检查订单当前版本及归属；记录幂等请求 ID。大批量操作分批事务提交并记录进度，重试仅处理未完成部分。
- [x] 增加“待归档”页面区域，显示身份观察值、订单数量、租赁类型、推荐理由和冲突；批量操作只提交具备 `customers:write` 的人员明确选中的记录。

**主要文件：** `cloud_functions/manageCustomers/`、`src/hooks/useCustomers.ts`、`src/pages/Customers.tsx`；根据复杂度新增归档组件及运维脚本。

**验收：** dry-run 零写入；重复扫描无重复候选；人工确认前订单归属不变；同组可分给不同客户；重复确认、并发修改、扫描中断后恢复均不重复建档或覆盖已确认归属；拒绝和忽略结果不会被重跑清除。

## 6. 阶段 4：接入全部订单入口与失败补偿

**目标：新订单与现有业务流程共用同一关联服务。**

- [x] 实现 `ingestOrder`，处理明确选择、衍生订单可信继承、唯一精确匹配和待确认四种情况；前两种不属于系统依据共享字段自动推断身份。
- [x] 统一接入 `saveOrders`、`updateOrder`、`importOrderFromAssist`、`manageAfterSaleOrders`，覆盖插件普通导入、续租和追加修改路径。
- [x] 校验前端续租/转租赁 2 草稿的来源关系；继承前解析有效客户。身份资料发生冲突或不能可信继承时转待确认，不机械复制旧 ID。
- [x] 普通编辑快照不自动改变客户归属；重关联使用显式操作，不能因为表单提交全量字段就重置归属及关联时间。
- [x] 关联操作人和时间由后端生成；内部服务以云函数内模块调用实现，操作人来自真实登录鉴权或已验证的插件 token，不允许客户端伪造内部模式绕过鉴权。
- [x] `CustomerOrderLinkFields.tsx` 改为受限远程搜索；补齐快捷创建客户，以及显式“保存为别名/新收件档案”。创建能力按 `customers:write` 控制。
- [x] 匹配在订单提交成功后执行；失败输出脱敏日志，并通过持久任务或可重扫状态重试。新订单自动关联仍由开关控制。
- [x] 手工未选择客户仍可保存为 `pending`；后台扫描可补齐未成功生成的候选。显式解除关联不得被补偿立即重新绑定。

**验收：** 手工、插件、续租、售后、转租赁 2 分别覆盖唯一匹配、无匹配、多匹配及服务异常；匹配异常时订单仍成功；旧客户端可保存；篡改引用 ID 被拒绝；临时收件修改不改主档；自动关联开关关闭时不产生自动归属。

## 7. 阶段 5：订单重关联、客户合并与撤销

**目标：提供可审计、可恢复的身份纠错能力。**

- [ ] 实现 `relinkOrder`，记录旧/新客户、所选引用、操作人和原因，更新归属但保留订单身份快照。
- [ ] 实现 `merge`、`unmerge` 和 `customer_merge_events`；源客户只建立映射，历史订单、别名和收件档案不搬迁、不改归属 ID。
- [ ] 拒绝自身合并、循环合并和无效/停用目标，并验证并发合并下的约束。
- [ ] 目标客户详情聚合客户簇；源客户默认隐藏，可筛选查看。新订单保存最终有效客户 ID。
- [ ] 明确链式合并撤销规则：有依赖的后续事件按逆序撤销或阻止当前撤销，不能清理错误映射。
- [ ] 撤销恢复原映射结构；合并后新建且写入目标客户的订单保留原存储归属，不臆测迁回源客户。
- [ ] 增加合并预览、历史来源提示、撤销入口及操作记录；涉及统计的修改登记受影响客户，供阶段 6 重算。

**验收：** A 合并到 B 后 B 可查双方历史；撤销恢复合并前的历史范围；链式合并与撤销可解释；历史订单关联 ID 和快照保持原值；重关联留下审计；无合并权限无法调用相关接口。

## 8. 阶段 6：客户统计和完整订单总览

**目标：客户详情中的汇总可从订单明细校验和重建。**

- [ ] 实现 `rebuildStats`，按客户簇遍历全部租赁 1/2 订单，计算总单数、分类型数量、累计金额、首次/末次日期。
- [ ] 新增、金额/日期/业务类型修改采用可靠增量；关联变化、合并、撤销使用全量重算。
- [ ] 补充设计入口清单外的 `deleteOrder`：删除前保留统计所需信息，成功后扣减或登记重算，避免删除后统计永久偏高。
- [ ] 用订单事件/版本及幂等处理避免重复增量，处理重算期间新写入和补偿重放；提供单客户及批量核对能力。
- [ ] 修正收件档案使用次数：以订单实际引用去重计算或幂等维护，不能因重复编辑增加次数。
- [ ] 客户列表增加业务汇总；详情提供租赁 1/2 筛选、服务端分页、明细跳转，替换仅展示最近 20 条的限制。
- [ ] 完成客户列表/搜索分页和索引查询；查询失败明确显示错误，不能静默显示零订单冒充真实结果。

**验收：** 多货品、旧扁平订单、续租及售后单按既定口径计算；增改单、删除、重关联、合并和撤销后统计与全量明细一致；重复补偿不多计；独立重建能纠正缓存；超过 20 条历史订单可完整查阅。

## 9. 阶段 7：客户关系与关系候选

**目标：将共享信息变为可解释候选，经人工确认后才形成关系。**

- [ ] 新增 `customer_relations`、`customer_relation_candidates`，实现 `listRelations`、`listRelationCandidates`、`confirmRelation`、`rejectRelation`、`removeRelation`。
- [ ] 根据有效完整电话、标准化地址、电话地址组合和历史收件档案生成证据，记录次数及证据版本；增加可恢复的关系候选扫描入口。
- [ ] 客户对先解析有效客户簇，排除同一客户的别名、自关系、空值、无效值和仅同名情况。
- [ ] 双向关系以排序客户 ID + 类型去重；有向关系保留起点和终点；“其他”必须填写方向和备注。
- [ ] 拒绝结果与证据版本关联；无新证据不重复提示。移除关系保存审计记录。
- [ ] 明确合并后的关系展示和撤销恢复规则：查询时解析映射并隐藏簇内关系，保留原端点及记录，避免撤销后信息丢失。
- [ ] 客户详情增加关联客户页签；客户管理增加关系候选区域、证据说明、确认和拒绝操作。

**验收：** 共享信息不会自动建关系或合并客户；双向不重复，有向语义正确；被拒绝且证据未变的候选不再提示；合并及撤销后关系展示正确；关系修改按客户维护权限校验。

- [ ] 准备集合、索引、权限、规则版本回填及开关清单；明确回滚版本、任务游标和错误补偿方式。
