# 客户建模阶段 4：订单入口接入与失败补偿

> 2026-09-07：本地实现完成；未部署云函数、未修改生产权限/配置或生产订单。自动匹配默认关闭。

> 后续发布记录：为修复扫描报错，已单独发布 `manageCustomers` 及归档所需结构，首批扫描成功；详情见[阶段 3 发布修复](./customer-modeling-phase3.md)。其它四个订单入口尚未发布，自动匹配仍未开启。

## 用户可见功能

- 新增订单可选择已有客户，也可快捷新建客户。具备 `customers:write` 才显示建档、保存别名、保存收货档案三个按钮；后端仍单独校验权限。
- 保存别名或收货档案前展示所属客户及将保存的信息。资料独立保存，取消录单也保留这些资料；请求使用已有幂等机制，网络失败重试沿用原请求 ID。
- 临时修改订单收件信息不会修改客户主档。新建订单时，若所选档案与本次收件快照不一致，服务端清除该档案引用，但保留明确选择的客户。
- 普通订单编辑仅展示当前客户归属，保存时保留归属、引用、时间、操作人；旧版本全量表单和点路径字段也不能覆盖这些字段。改绑/解除关联属于阶段 5。
- 未选择仍可保存。清除本次客户选择后，本次订单不执行自动匹配；后续仍可进入人工归档。

## 四个入口

| 入口 | 行为 |
| --- | --- |
| `saveOrders` | 验证真实登录用户及 `orders:create`；每条订单单独事务。明确选择的引用必须有效且属于同一最终客户簇，订单与人工关联审计一起提交。批量中一条失败不阻止其它条。保存完成后再匹配或继承。 |
| `updateOrder` | 验证真实登录用户及 `orders:update`；过滤关联字段和来源关系字段，沿用原有订单/待出库型号同步事务。普通编辑不触发身份推断。 |
| `importOrderFromAssist` | 沿用已有服务端 API token 验证，关联操作人固定为 `service:hc-order-assist`，不相信插件声明的操作人。普通导入、插件售后和续租保存后进入统一服务；追加货品保留归属，仅允许重试已有服务端 pending 标记。 |
| `manageAfterSaleOrders` | 沿用真实用户权限、原订单售后资格校验及幂等建单。取消直接复制旧客户 ID/关联时间，保存后重新验证来源并继承。 |

手工续租、转租赁 2 和售后会核对来源订单 ID、类型、客户名称、渠道、平台订单号以及派生产品类型。可信继承解析合并链至有效客户，不能把停用、缺失、跨客户引用带入新订单。收货档案仅在本次收件信息仍与有效档案一致时继承。来源冲突保留 `pending`，不通过自动匹配绕过。

插件续租不依赖历史订单才能创建。保存后按平台订单号与渠道寻找唯一符合条件的来源（最多 100 条，达到上限或多个符合来源时保守待归档），再在事务内重新核验来源。来源不存在、歧义或查询失败均不影响续租单已保存的结果。

## 内部服务、开关和并发

共享源代码为 `cloud_functions/manageCustomers/orderIngestion.js`。通过 `npm run customers:sync-order-modules` 同步到四个独立部署目录的 `customer/`，测试前检查副本一致性。采用云函数内直接模块调用，不需要开放跨函数调用凭证或接受 `internal=true`；`manageCustomers` 的客户端 `ingestOrder` 动作继续拒绝，包括通配管理员。

`system_config` 中文档 `customer_modeling` 的 `autoLinkNewOrders` 必须为布尔 `true` 才启用新订单自动匹配。开关缺失、关闭或读取失败不会产生自动归属。明确手工选择与可信派生继承不受该自动推断开关影响。

客户主档、别名、收货档案的事务维护和归档建档会同步递增 `system_config/customer_identity_revision.revision`。自动匹配在扫描前读取版本，提交事务内重新核验开关和版本，并写入版本文档以串行化关联与客户资料变更，避免扫描后新增/修改客户造成过期的“唯一匹配”。未来合并/撤销等身份写入也必须参与该版本机制。订单本身在关联事务内重新读取，人工忽略或其它并发编辑优先保留。

自动匹配严格使用阶段 2 的完整唯一精确规则，评分不能代替规则。事务写入订单引用与脱敏审计，重复运行不会再次写关联。当前匹配仍扫描三个主档集合，适合现阶段数据规模；大规模检索优化在阶段 6。版本文档形成串行点，上线前需测实际负载。

## 失败补偿

新租赁订单保存时由服务器写入：

- `customerIngestVersion: 1`：只有本阶段新入口产生的订单参与即时自动匹配，历史缺失版本订单不被自动认领。
- `customerIngestState: pending/done`：服务中断、来源冲突或匹配异常保留可重扫状态。
- `customerIngestActor`：服务端识别的初始操作人。
- `customerLinkStatus: pending/linked`、关联方式 `manual/inherited/exact`，实际关联时填写服务端操作人及时间。

状态与订单同时提交，即使函数在提交后立即中断，也不需要另一个任务写入成功才能发现遗漏。匹配错误日志只记录订单 ID 和稳定错误码；失败不返回匹配中的客户快照。

补偿使用阶段 3 的“客户管理 → 待归档”：管理员预览并扫描，生成候选，客户维护人员人工确认。没有新增后台定时自动认领任务；明确忽略或已关联的订单不会被补偿重新绑定。扫描候选与自动匹配并发时，归档确认前会再次检查当前订单归属，拒绝覆盖。
