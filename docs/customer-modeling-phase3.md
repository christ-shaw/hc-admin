# 客户建模阶段 3：历史扫描与人工归档

> 2026-09-07：已更新生产 `manageCustomers` 并补齐归档所需集合和索引，修复“新建扫描任务 → 不支持的操作类型”。使用当前管理员页面完成首批真实扫描：检查 20 条、符合条件 19 条、跳过 1 条、错误 0 次；仅生成候选，未修改订单归属。

> 后续进展：订单入口接入已完成本地实现，见[阶段 4 说明](./customer-modeling-phase4.md)。

## 交付功能

- 历史租赁 1/2 订单扫描，默认 dry-run；服务端单次请求最多读取 100 条；页面一次点击最多检查 500 条，内部连续执行 25 个每次 20 条的短请求。
- 候选按标准化身份指纹分组，展示观察值、数量、租赁类型、匹配评分与原因；不扫描普通销售单，不触碰已关联或已忽略订单的归属。
- 每个订单独立保存归档状态，支持同组拆分给不同客户。组内跨页明确勾选最多 100 条，再确认处理；没有自动勾选或自动提交。
- 处理方式：归入已有客户、新建客户并归档、填写原因忽略、填写原因拒绝某个推荐。归档可选择新增别名和收货档案，相同资料会复用。
- 原订单客户名称、收货人、电话、地址及业务字段保留原值。归档仅写客户关联字段；忽略只写忽略状态、原因和操作时间/操作人。
- 扫描与确认均保存进度。扫描失败可继续原任务；归档每次最多执行 10 个单订单事务，前端继续调用直至本次选择完成，网络中断后从“未完成的处理”继续。

## 接口

所有接口仍由 `manageCustomers` 鉴权和分发。新模块：`archiveScanner.js`、`archiveQueries.js`、`archiveResolver.js`、`archiveTarget.js`、`archiveCommon.js`。

### scanUnlinkedOrders

```ts
// 只读预览；默认 dryRun=true，不创建任务、候选或成员
{ action: 'scanUnlinkedOrders', dryRun: true, cursor: '', limit: 20 }
// 正式扫描；新任务从头开始，续跑只信任服务端已保存游标
{ action: 'scanUnlinkedOrders', dryRun: false, taskId: 'uuid-request-id', limit: 20 }
```

权限：操作权限 `*`。普通 `customers:write` 不开放历史扫描。每批按 `_id` 升序推进；数据读取失败不能解释为“没有订单”。任务保存 `running/failed/completed`、游标、已检查/符合条件/跳过数、累计错误次数及最近 20 条脱敏错误（订单 ID、错误码）。每个订单的候选更新与游标推进在同一事务提交；中断后从上一已提交游标继续。

每批只加载一次客户相关集合并缓存相同身份的匹配结果。推荐最多展示 50 位客户，`matchCount` 保存完整数量；这不影响人工搜索其它客户。dry-run 返回订单 ID、类型和匹配摘要，不返回原始身份资料，也不写数据。

扫描不反向覆盖已处理成员。订单身份变化时，把仍待处理的成员移到新候选，并更新两组计数；外部已关联或不再符合条件的待处理成员标记 `stale`。在游标之前插入或修改的订单由新一轮任务重新扫描；任务完成不表示后续新增订单已被处理。

### listLinkCandidates

| view | 返回内容 | 分页 |
| --- | --- | --- |
| `candidates`（默认） | 候选组，支持 `status=pending/processed/all` | 默认 20，最多 50 |
| `members` | 指定 `candidateId` 的成员，支持 `pending/accepted/ignored/stale/all` | 默认 20，最多 50，按订单序号升序 |
| `requests` | 当前操作人未完成归档请求的摘要，不返回原始处理计划 | 默认 20，最多 50 |
| `tasks` | 扫描任务状态和计数 | 默认 20，最多 50 |

权限：客户读取能力。页面显示扫描操作还要求 `*`；处理按钮要求 `customers:write`。订单新增/编辑权限不能读取归档候选或调用确认接口。

### resolveLinkCandidate

```ts
{
  action: 'resolveLinkCandidate', requestId: 'uuid-request-id',
  mode: 'link', // create / link / ignore / reject
  candidateId: '候选指纹', evidenceVersion: '页面读取到的证据版本',
  members: [{ memberId: '成员ID', revision: 1 }], // 仅明确选择的成员，1～100条
  customerId: '目标客户ID',
  // create 时填写 displayName；ignore/reject 时必须填写 reason
  // 可选 newAlias: {name, salesChannel}、newRecipient: {consignee, phone, address, label}
  // 服务端也支持已选 customerAliasId / recipientProfileId，并校验同一有效客户簇
}
// 续跑已授权并保存的原计划，不能在续跑时修改选择或目标
{ action: 'resolveLinkCandidate', requestId: 'uuid-request-id', resume: true }
```

权限：`customers:write`。处理计划限定为同一候选组；不同身份组分别核对确认。返回 `requestId/status/next/total/results/customerId`。逐条结果包括 `accepted/ignored/rejected/conflict`，冲突附错误码。结果不会把其它订单隐式加入本次处理。

## 数据、并发与重跑

- `customer_link_candidates` 不再存储无限增长的 `orderIds`。保存身份观察值、规则版本、证据版本、推荐摘要、总数/待处理数和两个租赁类型计数；组状态是 `pending/processed`，不把部分处理的组整体标为已接受或已忽略。
- `customer_link_candidate_members` 以订单 ID 生成确定性文档 ID，独立保存所属候选、订单全记录摘要、成员修订号、证据版本、拒绝客户 ID 和处理结果。一个订单只有一个成员记录。
- 同一证据版本下，重扫保留拒绝列表。拒绝只排除该推荐，不自动忽略订单；新的证据版本可以重新提示，旧拒绝原因和证据版本保留在审计记录中。
- 确认必须同时满足：成员仍待处理、成员修订号一致、成员及候选证据版本一致、当前订单仍可归档、订单摘要及身份指纹未变化。摘要使用稳定键顺序，不仅依赖可能缺失的 updatedAt。
- 新客户、初始别名、可选别名/档案和第一条有效订单在同一事务提交。全部选择发生冲突时不创建客户；任何持久化故障回滚当条事务，不留下半建档。
- 为已有客户新增资料时遵循阶段 2 的 `customers.writeRevision` 约定：先读取版本，再查询重复资料，事务内复核并递增版本。引用验证在任何写入前执行。停用客户、跨客户引用等明确冲突逐条记录；系统异常中断请求并保留已完成进度。
- `customer_write_requests` 增加 `action='resolveLinkCandidate'` 的请求记录。归档请求 ID 按操作人及归档作用域生成确定性键；保存经白名单校验的处理计划、载荷摘要、进度、最多 100 条结果及已创建目标 ID。重复请求返回原进度/结果，不重复建档；改变请求内容要求新 ID。
- 审计包含动作、订单/候选/客户 ID、服务端操作人、时间、证据版本及人工原因；运行日志不输出客户名称、电话或地址。处理计划保存在服务端请求集合，不通过处理记录列表返回。

## 2026-09-11 归档证据版本误判修复

订单 1535 的失败记录为 `ARCHIVE_EVIDENCE_CHANGED`：请求携带的证据版本与候选组一致，但成员记录仍保存早期扫描版本。分批扫描同一身份组时，更新组推荐并不同时重写该组所有成员，原校验因而会持续拒绝早期成员，即使刷新页面仍不能归档。

归档改为校验用户核对的组证据版本，并继续检查成员所属组、待处理状态、成员修订号、完整订单版本及身份分组。处理成功时同步该成员证据版本，清除旧证据对应的拒绝推荐记录。旧页面引用过期组证据、订单变更、已归档和无效客户引用仍会拒绝；不直接修补业务数据或自动提交此前失败请求。

快速归档、批量归档和普通归档统一显示具体冲突原因；全部冲突时显示“本组未归档成功”，不再展示绿色成功提示。103 项客户测试和构建通过；回归测试覆盖分批扫描后 link/create 成功及旧证据仍拒绝。云函数修复仅涉及 `manageCustomers`，前端修改在本地，尚未发布静态托管。发布前备份：`/tmp/manageCustomers-before-archive-fix-20260911.zip`。
