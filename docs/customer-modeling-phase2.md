# 客户建模阶段 2：身份匹配与可靠写入

> 2026-09-06：本地实现完成；阶段 1、2 共 41 项自动化测试及前端构建通过。尚未部署、启用自动订单关联或执行生产结构初始化。

> 本文保留阶段 2 的交付记录；历史扫描及归档请求的进度、成员和审计扩展见[阶段 3 说明](./customer-modeling-phase3.md)。

## 交付范围

- `manageCustomers/index.js` 保留鉴权、分发和管理查询。数据访问、匹配、合并链解析/引用校验、资料整理、事务写入和审计分别拆到 `repository.js`、`matcher.js`、`cluster.js`、`records.js`、`writer.js`、`audit.js`。
- `matchIdentity` 只读返回最终客户、精确匹配资格、候选评分及证据对象 ID。客户端仍需客户读取能力；订单新增/编辑权限不能读取匹配证据，`internal=true` 无效。
- 客户及其初始别名在同一事务创建；客户、别名和收货档案的全部维护动作均写入事务内审计及幂等记录。
- 前端维护请求自动生成请求 ID；同一在途请求合并，失败后重试或刷新页面继续使用原 ID。浏览器 sessionStorage 只保存请求内容摘要与随机 ID，不保存姓名、电话、地址原文。
- 新增集合/索引清单、只读核验及显式初始化脚本。业务查询不再自动创建缺失集合；数据库错误不能被当作“没有候选”而继续自动关联。

## 匹配接口与规则

```ts
{ action: 'matchIdentity', identity: {
  customerName: '下单名称', consignee: '收货人',
  phone: '13800138000', address: '完整地址'
} }
```

`identity` 也兼容订单字段 `consigneePhone`、`consigneeAddress`。返回结构为 `{ success: true, data: ... }`：

| 字段 | 含义 |
| --- | --- |
| `status` | `exact`、`no_match`、`incomplete`、`ambiguous`、`invalid_cluster` |
| `autoLinkEligible` | 仅 `exact` 为真，是匹配判断结果，本接口不写订单 |
| `customerId` | 仅唯一精确匹配时返回最终有效客户 ID，其他情况为 null |
| `candidates` | 按评分降序、客户 ID 排序；包含 `score`、`reasons`、`evidence`、`exact`、`exactRecipientProfileIds` |
| `issues` | 停用或损坏合并链的客户 ID 和错误码，不含身份原文 |
| `normalizationVersion` / `identityFingerprint` | 沿用阶段 1 的标准化版本与确定性指纹 |

名称精确匹配计 40 分；电话、地址、收货人分别计 30、20、10 分。收货部分取同一份档案的最高分，不把多个档案的字段分数拼成 60 分。证据记录类型、来源及对象 ID，不回传姓名、电话、地址原文；分数只用于排序。

自动关联资格须同时满足：完整观察值、启用的主名称/别名证据、同一份启用且完整的收货档案全部一致、解析合并链后仅一个有效客户。掩码号码、不支持的电话格式、缺字段、单独同名/同电话/同地址均不足以自动关联。国家码按阶段 1 保留，不把 `+86` 和无国家码号码自动等同。

客户簇内合并源主名和启用资料可参与匹配，但结果归到最终有效客户。循环、缺失目标、空目标、状态与映射不一致、超过 100 层均有明确错误；若存在损坏的簇，唯一性不可确认，整次匹配返回 `invalid_cluster`。正常停用客户及指向停用目标的簇不参加匹配。

## 可复用引用校验

`cluster.validateCustomerReferences(repository, refs, store?)` 接收 `customerId`、可选 `customerAliasId` / `recipientProfileId`，返回解析后的最终客户 ID 与有效引用：

- 客户必须存在，合并链有效，最终状态为 active。
- 别名和收货档案必须存在、启用，归属于同一最终客户簇。
- 缺失客户、跨客户引用、停用资料明确失败，不改写任何订单快照。
- `store` 可传订单事务对象，以便阶段 4 在提交前从同一事务复查引用。该函数是服务端模块，不新增客户端“校验后直接写订单”的绕过入口；订单服务仍须先检查本人的订单操作权限和目标订单范围。

阶段 2 尚未修改各订单保存入口。无显式客户引用的订单是否匹配、如何失败补偿，以及合并后的管理详情/选择页聚合，分别在阶段 4、5 接入。

## 事务、并发和审计

所有维护动作必须带 `requestId`（8～128 位字母、数字、下划线或连字符）。无 ID 返回 `REQUEST_ID_REQUIRED`，同一用户复用 ID 提交不同动作/内容返回 `IDEMPOTENCY_KEY_REUSED`。请求记录以“服务端操作人 ID + requestId”的 SHA-256 为文档 ID，不使用客户名称作为唯一键；不同请求仍可人工创建同名客户。

事务内一次提交业务记录、`customer_operation_audits` 与 `customer_write_requests`。新建客户还原子创建初始别名；任一步失败全部回滚。提交成功但响应丢失时，原 ID 重试返回已保存结果。

`customers.writeRevision` 是客户范围的并发版本，旧记录缺失视为 0。维护子资料前先读取客户版本，再扫描启用别名；事务中复核客户版本和待修改记录，并递增客户版本。两个不同请求同时新增/改名/启用相同标准化名称及渠道的别名时，只允许一个成功。事务冲突最多重试四次，仍冲突时要求沿用原请求重试。后续归档、合并及订单服务写客户资料时也必须遵循此版本约定，不能绕过 writer 直接写子集合。

已合并客户不能编辑或通过启停恢复；停用客户须先启用才能维护子资料。审计只保存动作、客户 ID、对象 ID、服务端操作人、时间和变更字段名，不保存身份原文。幂等记录保存载荷摘要与结果，不设置自动过期，避免旧请求重试再次建档。

## 集合与索引

完整清单见 `scripts/customerSchema.cjs`。覆盖设计第 13 节，并预留合并事件、扫描任务、候选订单成员集合；新增请求与审计集合。客户名、电话、地址以及关系候选 pairKey 均未设置全局唯一索引；需要确定性键的对象由对应阶段使用文档 ID 实现。

```sh
# 只读：核验指定环境的缺失集合/索引
npm run customers:schema -- --env ENV_ID

# 结构准备：仅补建缺失项；不会自动删除或替换索引
npm run customers:schema -- --env ENV_ID --apply --confirm ENV_ID

# 离线演练：JSON 是集合名到索引数组的映射；空对象表示空环境
npm run customers:schema -- --input /tmp/customer-schema.json
```

地域默认 `ap-shanghai`，其他地域传 `--region`。脚本使用已登录的 CloudBase CLI，先确认环境对应的数据库实例。遇到同名不同定义索引时停止，不自动覆盖。初始化后重新核验；如果索引仍在构建或缺失，退出码为 2，需要稍后重跑核验。未完成核验前不要发布依赖新集合的云函数。
